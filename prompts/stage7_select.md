# Стадия 7 — Select

Один вызов на заёмщика, все пункты сразу. Модель распределяет транзакции по ролям.
Возвращает только идентификаторы.

## Вход

```
<covenants>
  на каждый пункт: clause_id, дословный текст пункта, role_descriptions из стадии 6
<related_parties>
  уже отфильтрованные кодом по порогу — только те, кто прошёл
<adjustments>
  корректировки из стадии 6, чтобы модель их учитывала, а не выбирала заново
<transactions>
  ВСЕ транзакции счёта: txn_id | date | counterparty | description | amount | currency
```

Полный срез — 54–59 строк, примерно 3 КБ. Никакой предварительной фильтрации: модель
должна видеть и то, что не подходит, иначе не сможет отличить «единственную статью
операционных расходов» от «всего, что похоже на расход».

## Системный промпт

```
Ты распределяешь банковские транзакции по ролям финансовых показателей.

ГЛАВНОЕ ПРАВИЛО

Возвращай ТОЛЬКО идентификаторы транзакций. Никаких сумм, итогов, коэффициентов
и выводов о соблюдении. Все расчёты выполняет программа.

КАК ВЫБИРАТЬ

1. Роль определяется формулировкой ЭТОГО пункта, а не общим смыслом описания
   транзакции. Если пункт называет «Операционные расходы» и в реестре есть строка
   «Plant operating and maintenance expenses» — это она. Аренда, страхование,
   маркетинг и налоги в эту роль НЕ входят, даже если они очевидно расходы.

2. Рассматривай каждый пункт независимо. Не переноси выбранные транзакции между
   пунктами. Одна и та же операция может входить в один пункт и не входить в другой —
   это нормально и ожидаемо.

3. Большинство ролей содержит одну–три транзакции, а не десять. Если набралось много,
   перепроверь: скорее всего ты трактуешь роль шире, чем написано в пункте.

4. Каждая роль должна получить хотя бы одну транзакцию. Если ни одна не подходит
   идеально, выбери наиболее близкую по существу операции и укажи её также в
   uncertain как low-confidence. Пустая роль допустима только если во всём реестре нет ни одной
   операции такого рода: это редкое исключение, а не рабочий вариант.

   Для каждой роли пройди все транзакции реестра, отберёшь те, чьё описание
   соответствует формулировке роли по существу операции. Из отобранных возьми все,
   если описания однотипны, либо наиболее точное совпадение, если они разнородны.
   Обычно в роли одна–три транзакции.

   Не требуй буквального совпадения слов. Для операционных расходов однотипны, например,
   обслуживание производства, техническое обслуживание, регенерация оборудования и иные
   услуги, поддерживающие основную деятельность; их нужно выбрать вместе, если они
   соответствуют одной роли.

5. Знак суммы в реестре не определяет роль. Расходы записаны отрицательными,
   поступления положительными; выбирай по существу операции.

   Валюта не влияет на выбор роли. Транзакция в EUR или другой валюте выбирается
   наравне с долларовыми; пересчёт в USD выполнит программа до суммирования роли.

6. Корректировки применяет программа, не ты. Если транзакция упомянута в блоке
   <adjustments>, выбери её в роль, соответствующую её ИСХОДНОМУ описанию в реестре,
   и никогда в целевую роль корректировки. Например, операция описана как
   консультационные услуги, а в adjustments сказано «переклассифицирована в Процентные
   расходы»: выбери её как консультационные услуги и НЕ добавляй в роль процентных
   расходов. Двойное включение — самая частая ошибка на этом шаге.

7. Роль related_party: код уже отобрал связанные стороны по доле владения.
   Выбирай платежи только этим контрагентам. Имя в реестре может отличаться —
   встречаются запятые и приписки в скобках вида «(Turkistan point)».
   Совпадение по основному наименованию достаточно.
   Это единственный случай, когда пустая роль законна.

8. uncertain — не замена выбору. Если транзакция подходит под роль сомнительно,
   всё равно выбери её в наиболее подходящую роль и дополнительно перечисли в
   uncertain с коротким пояснением: это пометка «проверьте меня», а не отказ решить.
   Идентификатор из uncertain ОБЯЗАН одновременно находиться в указанной там роли;
   иначе ответ недействителен.

ЧЕГО НЕ ДЕЛАТЬ

Не придумывай txn_id, которых нет во входных данных.
Не объясняй выбор длинным текстом.
Не считай суммы даже для самопроверки.

НЕПРАВИЛЬНО: {"6.1": {}, "uncertain": [...]} — роли не заполнены, ответ бесполезен.
ПРАВИЛЬНО: {"6.1": {"revenue": ["TXN-..."], "opex": ["TXN-..."],
"interest": ["TXN-..."]}}
```

## Схема ответа

```json
{
  "6.1": {
    "revenue":  ["TXN-B1-0026"],
    "opex":     ["TXN-B1-0023"],
    "interest": ["TXN-B1-0033"]
  },
  "6.2": {
    "payroll":   ["TXN-B1-0004"],
    "utilities": ["TXN-B1-0014"]
  },
  "6.3": {
    "related_party": ["TXN-B1-0030"]
  },
  "uncertain": [
    {"txn_id": "TXN-B1-0047", "role": "opex",
     "note": "аренда площадки, не подпадает под формулировку пункта"}
  ]
}
```

Ключи ролей берутся из `role_descriptions` соответствующего `CovenantSpec` — модель
не изобретает свои имена.

## Проверки поверх ответа

```python
assert all(t in ledger_slice for r in roles.values() for t in r)   # hard: выдуманный id
assert all(t.startswith(f"TXN-{scenario_id}-") for t in all_selected)
if not overlap(description_words(txn), role_description_words):     # soft
    warn(f"{txn} слабо соотносится с ролью {role}")
if any(len(v) > 8 for v in roles.values()):                         # soft
    warn("роль подозрительно широкая")
if any(len(v) == 0 for v in roles.values()):                        # soft
    warn("роль пустая")
```

Первые две проверки блокируют ячейку, остальные помечают для верификатора.

## Режим вызова

`SELECT_MODE=scenario` — по умолчанию: один вызов, все пункты. Дешевле, и модель видит
пункты рядом, что помогает не путать роли.

`SELECT_MODE=covenant` — один вызов на пункт. Втрое дороже, но исключает переток
между пунктами.

**Какой лучше — решает замер на local scorer, а не рассуждение.** Прогнать оба на всех
12 сценариях, сравнить средний балл и σ по `--repeats 3`, зафиксировать победителя
до 9 августа.

## Контрольный пример

На B1 правильный ответ известен: `revenue` = TXN-B1-0026, `opex` = TXN-B1-0023,
`interest` = TXN-B1-0033, `payroll` = TXN-B1-0004, `utilities` = TXN-B1-0014,
`related_party` = TXN-B1-0030. Пять транзакций из 57 плюс одна.

Типичные ошибки слабой модели, за которыми следить в трейсах: затягивание
`Depot yard rent` и `Warehouse contents insurance` в `opex`; включение
`Social tax remittance` в `payroll`; включение платежа `Irtysh Advisory Bureau`
в `related_party` (доля 18.6%, порог 20.0% — код его уже отфильтровал, но модель
может добавить по смыслу).
