# Halyk AI Challenge — пайплайн проверки кредитных ковенантов

Решение читает структуру задания из `submission_template.json`, обрабатывает
финансовые PDF-документы и реестр транзакций и для каждой пары
(заёмщик, пункт ковенанта) записывает `status`, `actual` и `evidence_txn_id`.
**Ни одно число в итоговом `submission.json` не приходит от модели** — LLM
возвращает только идентификаторы транзакций, дерево выражений и дословные
цитаты, а суммы и коэффициенты считает Python из CSV.

Ответы генерирует **этот собственный пайплайн** — `main.py` → `pipeline.py`
→ `stages/s{0,2,6,7,8,9}.py`. Anthropic Haiku и Sonnet вызываются как
компоненты через прямые HTTPS-запросы в `lib/anthropic_client.py`
(`urllib`, без готовых агентских SDK). Внешние агенты общего назначения
(Claude Code, Codex и т. п.) использовались только при разработке — на
прогоне их в зависимостях нет.

## Что пайплайн умеет находить

- Действующую редакцию договора против недействующей редакции 2024 года и черновой ведомости аудитора.
- Цепочку «аудиторское дело → номер отчёта → финальный AUP-отчёт», где лежит реклассификация.
- Переклассификации, отсечения периода, исправления сумм и отклонённые аудитором корректировки.
- Курс валюты, выводимый из пары сумм в аудиторском примечании, а не из таблицы курсов.
- Порог связанных сторон, извлекаемый из текста KYC (в публичном сете встречаются и 20 %, и 40 %).
- Транзакции с пустой суммой в реестре, восстановленные из служебной записки казначейства.
- Страницы PDF без текстового слоя, включая KYC-досье целиком в виде изображения.
- Условия применимости (springing) и оговорки-исключения, при которых `actual` выше лимита, а статус `COMPLIANT`.

## Запуск с приватным датасетом

```bash
# Linux / macOS
git clone <repo> && cd halyk_rag
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env             # затем впишите ANTHROPIC_API_KEY
python main.py run --fresh --data <path/to/private-dataset>
```

```powershell
# Windows (PowerShell)
git clone <repo>; cd halyk_rag
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env      # затем впишите ANTHROPIC_API_KEY
.\.venv\Scripts\python.exe main.py run --fresh --data <path\to\private-dataset>
```

`--data` временно подменяет `DATA_DIR` — там ожидаются
`submission_template.json`, `master_ledger_2025.csv` и папка `documents/` с
PDF-файлами. `--fresh` удаляет прошлые `workspace/extractions` и
`workspace/selections`, но сохраняет `workspace/vision` (vision-ответы
детерминированы, а платить повторно за одинаковый рендер страницы незачем).

После прогона `workspace/submission.json` — готовый файл.
`main.py score <submission> <ground_truth>` считает локальный балл, если у
организаторов есть ключ разметки.

`main.py view [--ground-truth <path>]` собирает self-contained HTML-трассировщик
в `reports/view.html` — таблица 12×N ячеек, клик по ячейке разворачивает всю
цепочку: документы (действующие + отклонённые), пункт договора с цитатой,
корректировки с источниками, выбранные транзакции, подстановку чисел в
формулу и контрфактический перебор кандидатов на evidence. Работает и без
`ground_truth.json` — тогда колонка со счётом просто не показывается.

## Замеренный холодный прогон на публичном сете (07 августа 2026)

Данные: `agentic-bank-public/` (12 заёмщиков, 36 ячеек, 200 PDF, 7 vision-страниц).

| Стадия               | Время   | Токены (in / out)     | Стоимость |
|----------------------|---------|-----------------------|-----------|
| 2 · PDF + vision + doctypes | 3.2 с | всё из кэша     | $0.00     |
| 6 · extract (Haiku)  | 139.2 с | 110 324 / 17 079      | $0.196    |
| 7 · select (Sonnet)  |  59.3 с | 130 226 /  3 553      | $0.296    |
| 8–9 · compute + evidence | 1.9 с | —                   | $0        |
| **всего**            | **204 с (3:24)** |                | **$0.492**|

**Балл на публичном сете: 0.8167** (86 % статусов, 31 из 36 верных).

Замерен на четырёх независимых `--fresh` прогонах: диапазон **0.72 … 0.82**,
среднее ≈ **0.78**, стандартное отклонение ≈ 0.05. Верхняя граница диапазона
после clause-level salvage и repair retry (см. ниже) достигается стабильно, а
не через раз, как было до этих правок. Нижняя граница поднялась с ~0.62 до
~0.77, потому что ни один сценарий больше не пропадает целиком: если Sonnet
портит одну клаузу, остальные две сохраняются.

Переименование сценариев `B1→T1`, `P3→T7` в шаблоне, реестре и кэше даёт тот
же балл 0.8167 (`tests/rename_test.py`) — прямое доказательство, что состав
задачи читается из `submission_template.json`, а не привязан к конкретным
именам публичного сета. Кросс-прогон анализ — `scripts/stability.py`.

## Тринадцать стадий

**0. Baseline submit.** Первая запись `submission.json` идёт сразу же —
   шаблон заполняется `status:"COMPLIANT"`, `actual:0.01`. Каждая успешно
   вычисленная ячейка перезаписывает baseline. Если прогон упадёт в середине
   или отдельная ячейка не посчитается — на диске остаётся валидный сабмит,
   а неудачные ячейки сохраняют baseline (не `null`).

**1. Ledger map + gap scan.** Читаем `master_ledger_2025.csv` строго
   типизированно: пустые суммы остаются `NaN`, а не превращаются в 0. Список
   `TXN-*` с пропущенными суммами уходит на стадию 5.

**2. PDF extract с постраничным vision-фоллбэком.** PyMuPDF читает текст по
   страницам. Если страница даёт меньше 80 символов — мы отправляем её
   картинку в мультимодальный вызов Claude Sonnet и сохраняем ответ в
   `workspace/vision/{doc}_p{n}.txt`. Vision-текст автоматически попадает в
   склеенный `DocRecord.text`, поэтому стадия 6 видит его в том же промпте,
   что и обычный текст, без отдельного patcher-слоя.

**3. Триаж с точечной нормализацией.** Регекс чинит только идентификаторы
   вида `A С С - 7 2 0 1` (пробелы и латиница/кириллица). Каждый документ
   получает тип-кандидат (`agreement/kyc/aup/audit_notes/noise`) по русско-
   и англоязычным маркерам. Если документ носит `ACC-XXXX` (то есть
   привязан к заёмщику), но регексы вернули `noise`, включается Level-2
   fallback — Haiku классифицирует по первым 1500 символам, результат
   кэшируется в `workspace/doctypes/`. Жёсткий предохранитель: если
   кандидатов больше 40, fallback пропускается целиком — защита от
   сценария, где на приватном сете сломалась кодировка. Документы не
   удаляются: `noise` означает «не входит в контекст стадии 6 без
   специального retrieval».

**4. Граф версий.** Проекты, черновики и недействующие редакции остаются в
   графе как `rejected` — их существование значимо (P10 6.1 требует отличать
   отклонённое от несуществующего).

**5. Targeted retrieval.** Для каждой транзакции с пропущенной суммой из
   стадии 1 ищем документ, где эта транзакция упомянута — служебная записка
   казначейства и приложение аудитора. Оркестратор передаёт такие документы
   стадии 6 в блок `<extra_documents>`. Параллельно ищется консолидированный
   отчёт по имени материнской компании — group capex восстанавливается
   формулой IFRS (end PPE − begin PPE + depreciation).

**6. Extract.** Один Haiku-вызов на заёмщика. Модель получает статью 6
   договора, аудиторские заметки, KYC и найденные на стадии 5 фрагменты.
   Возвращает `CovenantSpec`, `Adjustment`, `RelatedParty`, `DocumentFact` со
   ссылками и цитатами. Числа не считает — только переносит. Детерминированные
   стражи проверяют оператор, наличие `max`/`applicability`/`exception` и
   присутствие порога в цитате.

   Оркестратор `run_pipeline` вызывает `extract_scenario` для каждого сценария
   с отсутствующим кэшем и записывает результат в
   `workspace/extractions/{scenario_id}.json`.

**7. Select.** Один Sonnet-вызов на заёмщика. Модель видит ковенанты,
   `role_descriptions`, отфильтрованные кодом связанные стороны и **срез
   ленты только этого сценария**. Принадлежность транзакции сценарию
   определяется по ключу сценария из шаблона как токен внутри `txn_id`,
   а не по жёсткому префиксу `TXN-{scenario_id}-` — формат идентификатора
   в приватном сете может отличаться, конвенция важна одна: ключ сценария
   встречается как разделённый токен. Возвращает исключительно
   идентификаторы транзакций по ролям — никаких сумм. Полный ledger
   используется только для валидации, чтобы поймать межсценарные
   галлюцинации.

**8. Compute.** Ограниченное дерево выражений (`sum/add/subtract/divide/max/
   min/const/fact`, глубина ≤ 4) исполняется на нормализованных к USD
   значениях. Facts из `document_facts` подставляются вместо `sum`, когда
   значение приходит из отчёта, а не из ленты.

**9. Evidence.** Только для `BREACH`. Ограниченный пул кандидатов и три
   контрфакта (drop, revert adjustment, flip related-party). Записываем ровно
   тот `txn_id`, чьё удаление возвращает `COMPLIANT`.

**10. Validate.** Разделены `hard` (нарушение → ячейка не записывается,
    остаётся baseline) и `soft` (записывается, помечается `low_confidence`).
    Правило «hard»: конечное положительное `actual`, `status ∈ {COMPLIANT,
    BREACH}`, `evidence_txn_id` существует в ленте.

**11. Verify.** Резервировано за перезапросом low-confidence ячеек к Haiku —
    заглушка.

**12. Submit.** Атомарная запись `workspace/submission.json` после каждой
    успешно вычисленной ячейки: `NamedTemporaryFile` + `os.replace`.

## Стабильность прогона под LLM-вариативностью

Три механизма в стадии 7, вместе снижающие вариативность между прогонами
с 0.21 до 0.10 по спреду балла:

- **Clause-level salvage.** Валидация Sonnet-ответа расщеплена. Структурная
  ошибка (список вместо словаря, не тот тип элемента) → retry всего вызова.
  Семантическая ошибка внутри конкретной клаузы (uncertain-транзакция для
  роли, которая не заполнена в этой клаузе; пустая обязательная роль при
  наличии кандидата в `uncertain`) → эта клауза дропается в `{}`, остальные
  клаузы сценария сохраняются. Раньше одна ошибка Sonnet роняла все три
  ковенанта заёмщика в baseline; теперь только 6.1 уходит в baseline, а
  6.2 и 6.3 считаются нормально.
- **Repair retry.** При структурной ошибке retry не тем же промптом, а с
  дословным текстом ошибки валидации в блоке `<repair>`. Sonnet видит,
  что именно пошло не так, и почти всегда возвращает исправленный
  ответ. Если и второй ответ garbage — оба сырых ответа сохраняются в
  `workspace/selections/rejected/{scenario}.json` с полем `attempts` для
  разбора.
- **Health-строка.** В конце каждого прогона выводится одна строка
  внутренних сигналов, собранных из submission и `workspace/selections/`:

  ```
  health: baseline=3/36 computed=33 valid_selections=12 rejected=0 salvaged=3 retried=0 warnings=407
  ```

  На приватном сете, где ground truth недоступен, эта строка — единственный
  способ сравнить два прогона. Хороший прогон: мало `baseline`, ноль
  `rejected`, `valid_selections` равен числу заёмщиков. Плохой прогон —
  наоборот, и такой стоит перезапустить.

## Возобновление и изоляция ошибок

- Кэш стадий 6 и 7 хранится по файлу на сценарий. Повторный `main.py run`
  без `--fresh` пропускает уже посчитанные сценарии — прерванный прогон
  можно продолжить той же командой.
- Одна сбойная ячейка не роняет прогон: ошибка попадает в
  `workspace/errors.log`, а её ячейка остаётся baseline.
- Скрипт `scripts/stability.py` разбирает три подряд `run{1,2,3}_submission.json`
  и печатает per-cell классификацию (stable-correct / stable-wrong /
  coin-flip) — использовался для измерения диапазона выше.

## Обоснование ключевых решений

- **Workflow, а не автономный агент.** Поток управления в коде.
- **Никакого RAG, vector DB, LangGraph, fine-tuning.** Документы разделены
  чёткими маркерами (ACC-номер счёта, номер AR-отчёта, имя заёмщика).
- **Ни одно число не приходит от модели.** LLM возвращает только структуру
  и идентификаторы.
- **Haiku для extract, Sonnet для select и vision.** На стадии 7 Haiku
  теряет структуру при расширении контекста; Sonnet держит.
- **Ledger виден селектору только по своему сценарию.** Предотвращает
  межсценарные галлюцинации.
- **Клиент синхронный, без параллелизма.** 24 последовательных вызова
  укладываются в 3.5 минуты, никакого `429` не наблюдалось.

## Тесты

```bash
python -m pytest -q                        # Linux / macOS
```
```powershell
.\.venv\Scripts\python.exe -m pytest -q    # Windows
```

85 тестов, все зелёные, без обращения к живому API. `tests/conftest.py`
обнуляет `ANTHROPIC_API_KEY` на всю сессию, чтобы ни один тест случайно не
потратил токены — даже если у разработчика в `.env` лежит настоящий ключ.
Тесты покрывают, в частности, salvage и repair retry на стадии 7, invariant
на NaN в стадии 8 и полный набор health-signals — все три механизма выше
проверены `FakeClient` / `QueuedFakeClient` без единого HTTP-вызова.

## Лицензия PyMuPDF

Для извлечения текста используется PyMuPDF (AGPL-3.0). Для хакатона это
допустимо; перед использованием проекта вне его необходимо отдельно проверить
лицензионные условия.
