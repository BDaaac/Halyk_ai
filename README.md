# Halyk AI Challenge — пайплайн проверки кредитных ковенантов

Решение читает структуру задания из `submission_template.json`, обрабатывает финансовые
PDF-документы и реестр транзакций и для каждой пары (заёмщик, пункт ковенанта) записывает
`status`, `actual` и `evidence_txn_id`.

**Ни одно число в итоговом `submission.json` не приходит от модели.** LLM возвращает только
идентификаторы транзакций, дерево выражений и дословные цитаты; суммы и коэффициенты считает
Python из CSV. Модель не управляет маршрутом пайплайна: последовательность стадий и все
переходы заданы кодом; LLM используется только для структурированного извлечения и выбора
идентификаторов.

Ответы генерирует этот собственный пайплайн — `main.py` → `pipeline.py` → `stages/`. Haiku и
Sonnet вызываются как компоненты через прямые HTTPS-запросы в `lib/anthropic_client.py`
(`urllib`, без агентских SDK). Внешние агенты общего назначения использовались только при
разработке — в зависимостях прогона их нет.

## Быстрый старт для проверяющего

```bash
git clone <repo> && cd halyk_rag
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env                     # впишите ANTHROPIC_API_KEY

# воспроизвести наш сабмит из закоммиченного кэша — без обращений к API
python main.py run --data <public-dataset>

# прогон на новых данных
python main.py run --fresh --data <path/to/dataset>
```

Windows: `.\.venv\Scripts\python.exe` вместо `python`, `Copy-Item` вместо `cp`.

Три команды, которые работают **без API-ключа**:

| Команда | Что делает |
|---|---|
| `python main.py view` | Собирает `reports/view.html` — грид ячеек, клик разворачивает цепочку: документы (действующие и отклонённые) → пункт договора с цитатой → корректировки с источниками → выбранные транзакции → подстановку чисел в формулу → контрфакт для evidence |
| `python scripts/validate_submission.py --submission <path>` | Проверка формата по CASE: JSON парсится, верхнеуровневые поля непусты, набор сценариев и клауз совпадает с шаблоном, `status ∈ {COMPLIANT, BREACH}`, `actual > 0`, лишних ключей нет. Exit 1 при любой ошибке |
| `python main.py score <submission> <ground_truth>` | Локальный балл, если есть ключ разметки |

`--data` временно подменяет `DATA_DIR`; там ожидаются `submission_template.json`,
`master_ledger_2025.csv` и папка `documents/`.

## Воспроизводимость сабмита

Кэш стадий 2/3/6/7 закоммичен в `workspace/{extractions,selections,vision,doctypes}`. Запуск
`main.py run` **без** `--fresh` на том же датасете вернёт побайтно тот же `submission.json`,
что мы загрузили: каждая кэшированная стадия проверяет наличие файла на диске и возвращает
готовый результат. Обращений к API — ноль.

Границы гарантии названы честно, потому что их стоит знать до запуска:

- **Ключ кэша — stem PDF-файла.** Путь и датасет в ключ не входят. Если в другом датасете
  окажется файл с тем же именем, будет использован закешированный результат от **чужого**
  документа, молча и без предупреждения.
- **`--fresh` чистит только `extractions/` и `selections/`** (`main._drop_llm_caches`);
  `vision/` и `doctypes/` сохраняются для воспроизводимости и чтобы не оплачивать повторную
  обработку того же документа.
- Из двух пунктов выше следует практическое правило: **новый датасет запускайте в чистом
  рабочем каталоге** либо предварительно удаляйте `workspace/vision` и `workspace/doctypes`.
- **Проверок хэшей нет** — ни входных файлов, ни версий моделей, ни содержимого промптов.
  Смена `SELECT_MODEL`/`EXTRACT_MODEL` в `.env` кэш не инвалидирует.

## Ловушки датасета, которые решение обрабатывает

Каждый пункт — место, где наивный пайплайн промахнётся молча: без ошибки, но с неверной
ячейкой. Все закрыты кодом и покрыты тестами.

- **Тихая подмена версии.** Рядом с действующей редакцией лежит проект аудиторской ведомости
  за прошлый год. Пайплайн, берущий первое совпадение по типу, посчитает по черновику. Граф
  версий (`stages/s2_pdf.py`, `resolve_documents`) держит черновики в `rejected`, для расчёта
  берёт только `active`.
- **Обрыв цепочки «аудиторское дело → AUP-отчёт».** Реклассификация живёт в финальном отчёте,
  а найти его можно только через номер, спрятанный в аудиторском деле. Цепочка разрешается
  через `references` и `report_number` в стадии 4.
- **Отклонённые корректировки.** `_is_accepted` считает корректировку принятой по умолчанию
  (Haiku часто пропускает поле); отклоняет только явное `accepted: false`. Отклонённые
  сохраняются в графе — их существование значимо, отличать отклонённое от несуществующего
  требует сам текст ковенанта.
- **Курс валюты, не заявленный таблицей.** В аудиторском примечании стоит пара сумм
  («€72 146.75 → $83 690.23»), из которой курс выводится делением. Таблицы курсов в датасете
  нет; `fx_rate` в стадии 8 считает честно.
- **Порог связанных сторон разный по заёмщикам.** В публичном сете встречаются и 20 %, и 40 %.
  Хардкодить нельзя: `related_parties.threshold_percent` извлекается из текста KYC.
- **Пустая сумма в реестре.** Фактическую сумму даёт служебная записка казначейства, которую
  триаж пометит как `noise`. Стадия 5 находит её через `mentioned_txn_ids` и передаёт в блоке
  `<extra_documents>`. Это обратный ход — от пробела в леджере к документу, а не от документа
  к леджеру.
- **Сканированные PDF без текстового слоя.** KYC-досье целиком картинка. PyMuPDF отдаёт на
  такой странице меньше 80 символов, страница уходит в vision-фолбэк, ответ кешируется и
  подмешивается в общий `DocRecord.text`.
- **Springing-условия и оговорки-исключения.** Пункт может применяться только при выполнении
  условия либо содержать прямое исключение; при этом `actual` может быть выше лимита, а статус
  — `COMPLIANT`. `applicability` и `exception` — отдельные структурные поля `CovenantSpec`,
  стадия 8 проверяет их до сравнения с порогом.

## Тринадцать стадий

| # | Стадия | LLM |
|---|---|---|
| 0 | **Baseline submit** — валидный файл с заглушками до всякой обработки | — |
| 1 | **Ledger map + gap scan** — пустые суммы остаются `NaN`, а не превращаются в 0 | — |
| 2 | **PDF extract** — PyMuPDF постранично, при пустом текстовом слое → vision | Sonnet |
| 3 | **Триаж** — точечная нормализация идентификаторов, тип-кандидат по русско- и англоязычным маркерам | Haiku (fallback) |
| 4 | **Граф версий** — `active` / `superseded` / `draft`, отклонённые сохраняются | — |
| 5 | **Targeted retrieval** — поиск документов по номеру транзакции из стадии 1 | — |
| 6 | **Extract** — один вызов на заёмщика, весь разрешённый комплект | Haiku |
| 7 | **Select** — один вызов на заёмщика, только идентификаторы транзакций | Sonnet |
| 8 | **Compute** — дерево выражений на значениях, нормализованных к USD | — |
| 9 | **Evidence** — ограниченный пул кандидатов и три контрфакта | — |
| 10 | **Validate** — раздельно hard и soft | — |
| 11 | **Verify** — зарезервирована, см. ниже | — |
| 12 | **Submit** — атомарная перезапись после каждой ячейки | — |

**0. Baseline.** Шаблон заполняется `status: COMPLIANT`, `actual: 0.01` до первого вызова
модели. Каждая посчитанная ячейка перезаписывает заглушку. Падение в середине прогона
оставляет на диске валидный сабмит, а не пустоту.

**3. Триаж.** Регекс чинит только идентификаторы вида `A С С - 7 2 0 1` (пробелы, латиница и
кириллица вперемешку); остальной текст не трогается. Документ с `ACC-XXXX`, который регексы
отнесли к `noise`, уходит на Haiku-классификацию по первым 1500 символам. Предохранитель: при
более чем 40 кандидатах fallback пропускается целиком — защита от сломанной кодировки на
незнакомых данных. Документы никогда не удаляются; `noise` означает лишь «не входит в контекст
стадии 6 без специального retrieval».

**5. Targeted retrieval.** Параллельно ищется консолидированный отчёт по имени материнской
компании — group capex восстанавливается формулой IFRS (end PPE − begin PPE + depreciation).

**6. Extract.** Модель получает статью 6, аудиторские заметки, KYC и фрагменты со стадии 5 —
около 10 КБ, что позволяет связать перекрёстные ссылки. Числа не считает, только переносит.
Детерминированные стражи проверяют оператор, наличие `max` / `applicability` / `exception` и
присутствие порога в цитате; паттерны двуязычные (`не менее` / `not less than`,
`не должно превышать` / `shall not exceed`, `наибольшая из` / `greater of` и т. д.). Расхождение
стража с моделью даёт `soft_warning`, а не молчаливую правку.

**7. Select.** Модель видит ковенанты, `role_descriptions`, отфильтрованные кодом связанные
стороны и **срез ленты только своего сценария**. Принадлежность транзакции сценарию
определяется по ключу сценария как разделённому токену внутри `txn_id`, а не по жёсткому
префиксу `TXN-{scenario_id}-` — формат идентификатора на других данных может отличаться. Полный
леджер используется только для валидации, чтобы поймать межсценарные галлюцинации.

**8. Compute.** Ограниченное дерево выражений (`sum/add/subtract/divide/max/min/const/fact`,
глубина ≤ 4). `fact` подставляется вместо `sum`, когда значение приходит из отчёта, а не из
ленты.

**9. Evidence.** Только для `BREACH`. Пул кандидатов ограничен, контрфактов три: удаление,
откат корректировки, смена статуса связанной стороны. Корректировка попадает в кандидаты, только
если её `from_role` или `to_role` пересекается с ролями текущей клаузы: корректировка о
`payroll` ничего не говорит о клаузе про связанные стороны и не должна вытеснять настоящее
доказательство. Записывается ровно тот `txn_id`, чьё удаление возвращает `COMPLIANT`.

**10. Validate.** `hard` — ячейка не записывается, остаётся baseline: конечный положительный
`actual`, корректный `status`, `evidence_txn_id` существует в ленте. `soft` — ячейка
записывается, расхождение уходит в `workspace/errors.log`. Схема сабмита при этом не
расширяется: посторонних ключей в ячейке не появляется ни при каких условиях.

**11. Verify — зарезервирована намеренно.** Верификация в решении реализована детерминированно:
стражи стадии 6, раздельная hard/soft-валидация стадии 10, контрфактическая проверка evidence,
health-сигналы. LLM-верификатор добавил бы механизм, способный испортить верную ячейку с той же
вероятностью, с какой исправляет неверную; измерить этот баланс без серии прогонов невозможно.
Непроверенный механизм в решение не включается.

## Устойчивость к отказам

**Отказ одной ячейки не роняет заёмщика.** Незнакомая операция в дереве выражений, отсутствующая
роль или отсутствующий факт поднимают `UnsupportedSpecError` (отдельный класс, не подкласс
`ValueError` — чтобы широкий `except` не проглотил программные ошибки). Ошибка локализуется на
уровне ячейки: она получает безопасный fallback, остальные клаузы сценария считаются нормально.
Раньше такой случай уводил в baseline все три ячейки заёмщика.

**Clause-level salvage.** Валидация ответа селектора расщеплена. Структурная ошибка → retry
всего вызова. Семантическая ошибка внутри клаузы → дропается только эта клауза, остальные
сохраняются.

**Repair retry.** При структурной ошибке повтор идёт не тем же промптом, а с дословным текстом
ошибки валидации в блоке `<repair>`. Если и второй ответ негоден, оба сырых ответа сохраняются
в `workspace/selections/rejected/{scenario}.json` с полем `attempts`.

**Возобновление.** Кэш стадий 6 и 7 хранится по файлу на сценарий: повторный `main.py run` без
`--fresh` пропускает посчитанное, прерванный прогон продолжается той же командой.

**Health-строка.** В конце прогона печатается одна строка внутренних сигналов:

```
health: baseline=1/36 computed=35 valid_selections=12 rejected=0 salvaged=1 retried=4
```

Каждый прогон снимается в `runs/{timestamp}/` вместе с `health.json`, куда пишется ярлык
`recommendation` (`main._decide_recommendation`): `rejected > 0` → прогон сломан;
`baseline > 1` → сабмит валиден, но при наличии бюджета стоит повторить; иначе — годный
кандидат. `retried` и `valid_selections` в жёсткие критерии не включены: замеров, на которых
можно было бы обосновать ранжирование по ним, пока недостаточно.

## Замеры на публичном сете

Данные: `agentic-bank-public/` — 12 заёмщиков, 36 ячеек, 200 PDF, 7 vision-страниц.

**Воспроизводимый ориентир — 0.8611** (32 из 36 статусов, сумма 31.00/36). Прогон на
закоммиченном кэше, API cost $0, одинаков на любой машине. Изменение этого числа между чистыми
клонами означало бы регрессию в детерминированной части или в кэше.

**Измеренный fresh Stage-6/7 cold-run — 0.8889** (33 из 36 статусов, сумма 32.00/36),
2026-08-09. Запуск выполнен в отдельном чистом клоне; `--fresh` очистил `extractions/` и
`selections/`, а закоммиченные `vision/` и `doctypes/` использовались повторно:

| Стадия | Время | Токены (in / out) | Стоимость |
|---|---|---|---|
| 2 · PDF + vision + doctypes | 2.9 с | из кэша | $0 |
| 6 · extract (Haiku) | 128.7 с | 110 324 / 16 750 | $0.194 |
| 7 · select (Sonnet) | 56.7 с | 130 186 / 3 530 | $0.296 |
| 8–9 · compute + evidence | 2.0 с | — | $0 |
| **всего** | **190 с (3:11)** | | **$0.490** |

**0.8889 — одно наблюдение.** Повторный `--fresh` даёт другой выход стадий 6–7 и может дать
другой балл. Разброс измерен прямым контролем: тот же код на другом сэмпле LLM-выходов дал
0.8611 — разница ровно в одном статусе. Ранние замеры до clause-level salvage давали σ ≈ 0.05,
но относились к другой сборке и на текущей не переизмерялись. Воспроизводимый ориентир —
только число на закоммиченном кэше.

Оба балла — локальная метрика по формуле CASE §4 (`status 0.50 / actual 0.30 / evidence 0.20`,
равное усреднение по 36 ячейкам). Официальный балл может отличаться из-за неопубликованных
весов сложности; покомпонентная разбивка потерь — `scripts/loss_report.py`.

## Известные ограничения

Семантически близкие транзакции без детерминированного признака остаются источником
вариативности стадии 7; мы сознательно не добавляем dataset-specific правила для таких случаев.
Известные несоответствия исходных public-документов также не исправляются кодом вручную —
пайплайн следует содержимому документа.

## Отсутствие подгонки под публичный сет

`tests/rename_test.py` переименовывает сценарии в шаблоне, реестре и кэше (`B1→T1`, `P3→T7`) и
получает тот же балл — состав задачи читается из `submission_template.json`, а не привязан к
именам публичного сета.

`tests/rename_test_foreign_format.py` идёт дальше: `TXN-B1-0001` → `ACME-01-0001`, со сбросом
префикса `TXN-`. Балл не меняется — логика «ключ сценария как разделённый токен»
format-agnostic.

## Обоснование ключевых решений

- **Workflow, а не автономный агент.** Поток управления в коде, модель вызывается в трёх точках.
- **Никакого RAG, vector DB, LangGraph, fine-tuning.** Документы разделены чёткими маркерами:
  номер счёта, номер отчёта, имя заёмщика.
- **Ни одно число не приходит от модели.** LLM возвращает структуру и идентификаторы.
- **Haiku на extract, Sonnet на select и vision.** На стадии 7 Haiku теряет структуру при
  расширении контекста, Sonnet держит.
- **Селектор видит только свой сценарий.** Предотвращает межсценарные галлюцинации.
- **Клиент синхронный.** Текущий runtime укладывается примерно в 3 минуты, поэтому параллелизм
  не требовался; последовательное выполнение также упрощает rate-limit handling и
  воспроизводимость трассировки.
- **Ошибка модели должна быть громкой.** Стражи, инварианты, salvage — обвязка не делает модель
  умнее, но превращает тихий неверный ответ в явный сбой.

## Тесты

```bash
python -m pytest -q
```

101 тест, все зелёные, без единого обращения к живому API. `tests/conftest.py` обнуляет
`ANTHROPIC_API_KEY` на всю сессию, чтобы ни один тест не потратил токены даже при настоящем
ключе в `.env`. Покрыты, в частности: salvage и repair retry на стадии 7, инвариант на `NaN` в
стадии 8, фильтр релевантности кандидатов на стадии 9, локализация отказа до одной ячейки и
полный набор health-сигналов — всё через `FakeClient` / `QueuedFakeClient`.

## Лицензия PyMuPDF

PyMuPDF распространяется под AGPL-3.0. При использовании проекта за пределами условий хакатона
необходимо отдельно проверить совместимость лицензионных требований.
