# Halyk AI Challenge — пайплайн проверки кредитных ковенантов

Решение читает структуру задания из `submission_template.json`, обрабатывает
финансовые PDF-документы и реестр транзакций и для каждой пары
(заёмщик, пункт ковенанта) записывает `status`, `actual` и `evidence_txn_id`.
**Ни одно число в итоговом `submission.json` не приходит от модели** — LLM
возвращает только идентификаторы транзакций, дерево выражений и дословные
цитаты, а суммы и коэффициенты считает Python из CSV.

## Запуск с приватным датасетом

```powershell
git clone <repo> && cd halyk_rag
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env      # затем впишите ANTHROPIC_API_KEY
.\.venv\Scripts\python.exe main.py run --fresh --data <path\to\private-dataset>
```

`--data` временно подменяет `DATA_DIR` — там ожидаются
`submission_template.json`, `master_ledger_2025.csv` и папка `documents/` с
PDF-файлами. `--fresh` удаляет прошлые `workspace/extractions` и
`workspace/selections`, но сохраняет `workspace/vision` (vision-ответы
детерминированы, а платить повторно за одинаковый рендер странице незачем).

После прогона `workspace/submission.json` — готовый файл.
`main.py score <submission> <ground_truth>` считает локальный балл, если у
организаторов есть ключ разметки.

## Тринадцать стадий

**0. Baseline submit.** Первая запись `submission.json` идёт сразу же —
   шаблон заполняется `status:"COMPLIANT"`, `actual:0.01`. Каждая успешно
   вычисленная ячейка перезаписывает baseline. Если прогон упадёт в середине
   или отдельная ячейка не посчитается — на диске остаётся валидный сабмит,
   а неудачные ячейки сохраняют baseline (не `null`).

**1. Ledger map + gap scan.** Читаем `master_ledger_2025.csv` строго
   типизированно: пустые суммы остаются `NaN`, а не превращаются в 0. Список
   `TXN-*` с пропущенными суммами уходит на стадию 5.

**2. PDF extract с постраничным vision-фоллбэком.** PyMuPDF читает текст по
   страницам. Если страница даёт меньше 80 символов — мы отправляем её
   картинку в мультимодальный вызов Claude Sonnet и сохраняем ответ в
   `workspace/vision/{doc}_p{n}.txt`. Vision-текст автоматически попадает в
   склеенный `DocRecord.text`, поэтому стадия 6 видит его в том же промпте,
   что и обычный текст, без отдельного patcher-слоя.

**3. Триаж с точечной нормализацией.** Регекс чинит только идентификаторы
   вида `A С С - 7 2 0 1` (пробелы и латиница/кириллица). Каждый документ
   получает тип-кандидат (`agreement/kyc/aup/audit_notes/noise`). Документы
   не удаляются: `noise` означает «не входит в контекст стадии 6 без
   специального retrieval».

**4. Граф версий.** Проекты, черновики и недействующие редакции остаются в
   графе как `rejected` — их существование значимо (P10 6.1 требует отличать
   отклонённое от несуществующего).

**5. Targeted retrieval.** Для каждой транзакции с пропущенной суммой из
   стадии 1 ищем документ, где эта транзакция упомянута — служебная записка
   казначейства и приложение аудитора. Оркестратор передаёт такие документы
   стадии 6 в блок `<extra_documents>`. Параллельно ищется консолидированный
   отчёт по имени материнской компании — group capex восстанавливается
   формулой IFRS (end PPE − begin PPE + depreciation).

**6. Extract.** Один Haiku-вызов на заёмщика. Модель получает статью 6
   договора, аудиторские заметки, KYC и найденные на стадии 5 фрагменты.
   Возвращает `CovenantSpec`, `Adjustment`, `RelatedParty`, `DocumentFact` со
   ссылками и цитатами. Числа не считает — только переносит. Детерминированные
   стражи проверяют оператор, наличие `max`/`applicability`/`exception` и
   присутствие порога в цитате.

   Оркестратор `run_pipeline` вызывает `extract_scenario` для каждого сценария
   с отсутствующим кэшем и записывает результат в
   `workspace/extractions/{scenario_id}.json`.

**7. Select.** Один Sonnet-вызов на заёмщика. Модель видит ковенанты,
   `role_descriptions`, отфильтрованные кодом связанные стороны и **срез
   ленты только этого сценария** (`TXN-{scenario_id}-*`). Возвращает
   исключительно идентификаторы транзакций по ролям — никаких сумм.
   Полный ledger используется только для валидации, чтобы поймать
   межсценарные галлюцинации.

**8. Compute.** Ограниченное дерево выражений (`sum/add/subtract/divide/max/
   min/const/fact`, глубина ≤ 4) исполняется на нормализованных к USD
   значениях. Facts из `document_facts` подставляются вместо `sum`, когда
   значение приходит из отчёта, а не из ленты.

**9. Evidence.** Только для `BREACH`. Ограниченный пул кандидатов и три
   контрфакта (drop, revert adjustment, flip related-party). Записываем ровно
   тот `txn_id`, чьё удаление возвращает `COMPLIANT`.

**10. Validate.** Разделены `hard` (нарушение → ячейка не записывается,
    остаётся baseline) и `soft` (записывается, помечается `low_confidence`).
    Правило «hard»: конечное положительное `actual`, `status ∈ {COMPLIANT,
    BREACH}`, `evidence_txn_id` существует в ленте.

**11. Verify.** Резервировано за перезапросом low-confidence ячеек к Haiku —
    заглушка.

**12. Submit.** Атомарная запись `workspace/submission.json` после каждой
    успешно вычисленной ячейки: `NamedTemporaryFile` + `os.replace`.

## Возобновление и изоляция ошибок

- Кэш стадий 6 и 7 хранится по файлу на сценарий. Повторный `main.py run`
  без `--fresh` пропускает уже посчитанные сценарии — прерванный прогон
  можно продолжить той же командой.
- Одна сбойная ячейка не роняет прогон: ошибка попадает в
  `workspace/errors.log`, а её ячейка остаётся baseline.

## Обоснование ключевых решений

- **Workflow, а не автономный агент.** Поток управления в коде.
- **Никакого RAG, vector DB, LangGraph, fine-tuning.** Документы разделены
  чёткими маркерами (ACC-номер счёта, номер AR-отчёта, имя заёмщика).
- **Ни одно число не приходит от модели.** LLM возвращает только структуру
  и идентификаторы.
- **Haiku для extract, Sonnet для select и vision.** На стадии 7 Haiku
  теряет структуру при расширении контекста; Sonnet держит.
- **Ledger виден селектору только по своему сценарию.** Предотвращает
  межсценарные галлюцинации.
- **Клиент синхронный, без параллелизма.** 24 последовательных вызова
  укладываются в 3.5 минуты, никакого `429` не наблюдалось.

## Лицензия PyMuPDF

Для извлечения текста используется PyMuPDF (AGPL-3.0). Для хакатона это
допустимо; перед использованием проекта вне его необходимо отдельно проверить
лицензионные условия.
